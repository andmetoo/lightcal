# Validation and performance protocol

All numbers below are **proposed targets, not measured results**. Record results during the platform prototype and revise only through a documented decision.

## Resource targets

| Metric | Initial target |
| --- | --- |
| Hidden idle CPU | At most 0.1% average on the reference machine over 5 minutes |
| Hidden private working set | At most 30 MiB after warmup |
| Visible private working set | At most 50 MiB for either calendar mode |
| First launch to usable calendar | p95 at most 500 ms for 20 fresh-process starts under documented warm filesystem-cache conditions |
| Resident tray activation to first usable frame | p95 at most 100 ms across 50 activations |
| Packaged application payload | At most 20 MiB uncompressed, excluding debug symbols |

Choose and document a reference Windows 11 x64 machine with SSD before collecting numbers. Report CPU model, RAM, Windows build, graphics adapter, Rust/dependency versions, renderer, and power mode. Keep cold-cache starts as a separately labeled experiment. Include binaries and any required redistributable payloads when reporting size.

Use optimized builds without a debugger, repeat after a 60-second warmup, and record raw samples plus p50/p95 in the prototype PR. Define CPU as CPU-time delta divided by wall time and logical CPU count; report absolute CPU seconds too. Record private bytes alongside private working set so paging cannot hide allocation growth. Use Windows process counters and, where needed, WPR/WPA; record tool versions and capture method. Screen recordings or instrumented event-to-frame timestamps can validate activation latency; state measurement overhead.

Hidden mode must not repaint continuously, run a busy timer, or poll the tray. Check repeated open/hide cycles for memory/handle growth. Do not compare renderer results from different build profiles or machines as if they were equivalent.

## Functional and accessibility matrix

- Entry points: first launch, pinned launch when resident, app-button activation, tray toggle, right-click menu, Quit, crash/restart.
- Shell: Explorer restart, tray overflow, auto-hidden taskbar, monitor disconnect, restored window position, multi-monitor placement.
- Display: 100/125/150/200% scaling, mixed DPI, light/dark/system theme, high contrast, long labels.
- Input: mouse, keyboard-only use, focus loss, focus transfer between modes, and menu interaction without accidental dismissal.
- Accessibility: Narrator names, role/selection announcements, focus visibility, contrast, and no color-only selected/today distinction.
- Dates: leap years including century rules, December/January, first-weekday changes, ISO week-year boundaries, local midnight, timezone changes, and suspend/resume.
- Persistence: missing settings, malformed settings, unsupported schema, permission failure, and restart after interrupted replacement.
- Features: weekday display, gray-weekday subsets, current-month label/year matching, optional shortcut registration/conflicts, startup, and About GitHub/koona.app links.
- Events: checked-calendar filtering, zero/multiple sources, permission/provider failures, loading/stale counts, all-day/recurring/multi-day occurrences, DST and exclusive date boundaries. Use synthetic data for automated tests; keep live-provider checks explicit and read-only.
- Updates: stable-version comparison, no release, offline, timeout, rate limiting, invalid metadata/link rejection, and no implicit download/install/restart.
- Languages: English default on every OS locale; switch/restart persistence for English/Russian/Spanish/Japanese; missing-message fallback; localized dates/plurals/errors/accessibility; long strings and Japanese font fallback; no changes to source event text or user date/weekday preferences.

## Automation boundaries

Pure Rust unit tests cover date arithmetic and state transitions. Integration tests use a temporary `LIGHTCAL_DATA_DIR`. OS shell and accessibility behavior need real desktop smoke checks; a headless successful build is insufficient. Add regression tests for concrete defects, not snapshots duplicating the implementation.

Current checks: `bun scripts/check-docs.ts`, `bun test scripts`, `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, and `cargo test --workspace --locked`. The documentation check validates local file targets and whitespace, not external URLs, heading anchors, or YAML semantics.

## Review regression checks

- Browser sign-in cancellation is serialized with local credential persistence. Fixture tests cancel an attempt while it waits for the credential lock, reject older attempts after a retry, and preserve a completed save until its UI result is delivered. Browser consent and provider requests run outside this commit gate.
- A saved Google client configuration reaches Reconnect after a provider load, including an expired account after restart without runtime client settings. Its secret is excluded from preference JSON. About interaction fixtures exercise manual Download/Install in all four languages, block duplicate installation requests, and render verification failures while an update remains available; the fixtures never launch an installer.
- The displayed month heading and day cells are published as one UI snapshot. The grid is clipped below the header to keep their rendering regions separate. Month navigation is exercised through repeated previous/next clicks, date selections, Today, another date selection and further navigation across December/January. At 150% scaling, the regression check verifies both the month/year property and the rendered title pixels with a reused software-renderer buffer, including a return to the same month after selection and Today.
- The calendar popup refresh (ADR 0011) is checked headlessly with the design-canvas sample month (today Sunday 1 November 2026 at 14:05): the agenda orders all-day chips first, dims past events, marks Now and the next event, expands and collapses a row in place with time, duration, location and calendar, links an empty day to the next event, and steps one month per wheel notch over the grid. `--render-snapshots` writes `calendar-*.png` for today (light, dark, without week numbers), the expanded Design review and an all-day chip, the Copied state, the empty day with its Next link, December with the Today button, the keyboard focus ring, and ru, ja and es. Fixture tests cover Google `htmlLink`/`location`, Graph `webLink`/`location.displayName`, ICS `LOCATION` without a link, and the event-link allow-list. The fixtures never write the clipboard or open a browser; Copy and Open need a manual Windows check. A UI test clicks the header's − button and checks that it hides the calendar like Escape while Settings does not, and `calendar-september-header-{en,ru,es}-light.png` show the longest month names with Today, Settings and − in one header. On the current day Today folds away and the month arrows sit together; leaving it slides them apart over 180 ms. The header animates only for changes synced while the popup is on screen (any navigation: arrows, wheel, keys, the agenda's Next link). Like the tray toggle, that reads the native window, so a hidden or taskbar-minimized popup and headless snapshots show it settled, including the tray Today item that syncs before showing; the controller takes that probe as `on_screen`, so a UI test checks both answers without touching process-wide native state, and the existing native test covers hidden, shown, taskbar-minimized, restored and hidden windows, the navigation test clicks header controls by accessible label (debug builds keep Slint element debug info for this), and a fold test checks that a folded Today leaves only the arrows' 4 px gap and drops out of the element tree. The motion itself needs a manual look.
- The Date size setting ([ADR 0012](decisions/0012-date-size.md)) is checked headlessly: a UI test clicks the Larger option in Settings › Calendar through the production handler and checks the saved preference and the 352 × 444 calendar, and another pins the 432 / 432 / 444 heights from the Theme metrics. `--render-snapshots` writes `calendar-large-light.png`, `calendar-larger-light.png` and `calendar-larger-dark.png`, and the `settings-calendar-*.png` snapshots show the Date size row in all four languages. Each size at 150 % Windows display scale still needs a manual Windows check.
- The Koi pond switch ([ADR 0013](decisions/0013-koi-pond.md)) is checked headlessly: a UI test presses the switch in Settings › Calendar through the production handler, checks that it starts off, saves on, and turns off again, and other UI tests drive the koi clock through window views (swim, wait for events with no timer, stop), check which window messages wake the koi, and parse display on, off and dimmed broadcasts and check that the 960 s wrap fits every swim loop and tail beat. `--render-snapshots` writes `calendar-koi-light.png` and `calendar-koi-dark.png` at a fixed pond time, and `settings-calendar-end-light-<locale>.png` shows the Koi pond row in all four languages. Measured on November 3, 2026 (release build, 32 logical CPUs, synthetic calendars, 10 s warmup then 30 s): with the pond on and the popup hidden in the tray, Lightcal used 0 CPU-seconds and about 3 MiB private bytes. After the koi clock gained its once-a-second watch, three more hidden runs measured 0, 0.016 and 0 CPU-seconds (0.016 s is a single 15.6 ms accounting tick; a running koi timer would show every run). After the watch moved from a once-a-second timer to window events, three hidden runs measured 0 CPU-seconds each, so the hidden pond does not animate. The CPU cost while the popup is open with the pond on is **not measured**: an automated launch could not confirm the popup stayed on screen. It needs a manual Task Manager check with the popup open.
- Headless settings interactions cover enabling Windows calendars from the Accounts provider list, Google connection state flowing from the controller into the account card's Refresh and Sign in actions, selecting a readable calendar alongside Windows permission recovery (Open settings and Refresh), recording Ctrl + Alt + K with the key-cap recorder, clearing a shortcut in all four languages, one-field ICS validation/retry without duplicate submission, About links without scrolling, and disabling persisted automatic update preferences on About in all four languages after scrolling. `--render-snapshots` writes `settings-*.png` for every settings tab, Accounts state (first run, signing in, cancelled, connection error, ICS link and its checking/error states, needs attention, offline, no selection, no calendars, Add account, Windows access denied), shortcut conflict, About state (idle, checking, up to date, update available, install error, offline, error), light and dark, and every tab in Russian, Spanish and Japanese. These checks use temporary data and callback fixtures; they do not open browsers, bind native shortcuts, connect providers or install updates.
- Window geometry reuses the shared work-area clamp. Tests include the current 448 by 360 settings layout at 200% DPI on a 1920 by 1040 work area, a legacy oversized stress case, oversized windows in both axes, and negative monitor origins. An oversized layout is anchored safely rather than causing invalid clamp bounds; this does not claim that its entire content fits a smaller screen.
- Calendar refresh robustness: a panicking provider call is caught by `run_load_guarded`, and a 90 second UI-thread watchdog releases the in-flight guard if a provider call never returns (status "Calendar refresh timed out"); a stale result releases the guard only when it belongs to the current request. Pure helpers (`watchdog_should_expire`, `stale_result_releases_guard`) are unit tested; the real timer and a hung provider are not exercised headlessly. The preferences recovery warning is shown on the General settings tab until dismissed, and account actions do not clear it.
- Measured on 2026-11-01 (Windows, `cargo build --release -p lightcal --locked`, `opt-level = "z"`, thin LTO, stripped): `lightcal.exe` is 13,089,280 bytes with `panic = "abort"` and 15,398,912 bytes with the default unwinding panic strategy (+2,309,632 bytes, +17.6%). These are file sizes, not memory measurements. Both are below the 20 MiB packaged payload target, so the release profile no longer sets `panic = "abort"`: with abort, the `catch_unwind` guard in `run_load_guarded` could not protect release builds, and a provider panic ended the process. The cost is the +17.6% file size above; revisit it if the payload target or a memory measurement changes.
- A process-owned offscreen native Windows window tests visibility, taskbar-style minimization, restoration, and hidden state. Tray and shortcut toggles read native state rather than a controller visibility flag. Dismissal minimizes the existing window and preserves its HWND for Explorer and DWM.
- Fixture snapshots preserve `AccessDenied` through provider aggregation and retain other providers' sources and events. Headless settings renders cover denied-only and mixed readable/denied sources in both themes; permission-recovery controls and readable calendar selection must coexist.
- A long preferences recovery warning wraps on the App tab (up to four lines) and pushes the settings card down; the card shrinks and scrolls instead of overlapping the footer. `warning-app-en-dark/light.png` and `warning-app-ja-dark.png` from `--render-snapshots` cover it. A calendar load that exceeds the 90 second watchdog unlocks the UI with a localized message but stays valid, so a late result is still applied unless a newer request has started.
- Window chrome (ADR 0011), checked on 2026-11-01 on Windows 11 build 26300 at 150% scaling with `--compact --synthetic-calendars` and a temporary `LIGHTCAL_DATA_DIR`. Before the change the frameless window had no shadow. After it, `DwmGetWindowAttribute` reads back `DWMWCP_ROUND` for the window in both views, and screen captures over a flat backdrop show the system shadow around the calendar and settings. No frame extension is needed for the shadow. A unit test applies the chrome to an offscreen window and accepts either outcome, so Windows 10 runners pass; Windows 10 itself was not checked by hand. The DWM preview subclass and `DWMWA_HAS_ICONIC_BITMAP` are unchanged; the live Explorer thumbnail and Peek were not re-checked by hand.
- Window and taskbar icon, checked on 2026-11-03 on Windows 11 build 26300 at 150% scaling with a debug build. Before the change, Alt+Tab and the taskbar button showed Windows' generic icon: Slint 1.18.1 never forwards a window icon built from a pixel buffer, so `WM_GETICON` returned nothing. After it, `WM_GETICON` reads back a 64 px big icon and a separate 24 px small icon (the shell's small-icon size at that scale) on the running window, and both remain after a `WM_SETTINGCHANGE` sent to it. Unit tests cover the icon pixels and sizes, rebuilding only when the inputs change, moving to a new window, clearing on drop, retrying a failed build, the display-change hook, the size cache and the tray update decision. A test fails on any Slint update so the workaround is re-checked. The owner then saw the dated icon in Alt+Tab and on the unpinned taskbar button, and the static app icon once the button was pinned, as Windows draws a pinned shortcut's own icon (ADR 0010). These were not captured by screenshot; a live display-scale change and the Linux gate were not run.
- Mica prototype (`LIGHTCAL_MICA=1`, off by default). DWM reads back `DWMSBT_MAINWINDOW`, and the client area is extended into the frame. The backdrop is **not visible yet**, because the Slint calendar and settings surfaces are opaque; showing it needs a transparent or translucent Slint root, which is a UI decision. Release build (`cargo build --release -p lightcal --locked`), visible calendar, 60 second warmup, then a 60 second window, two runs per setting in alternating order, on an AMD Ryzen 9 9950X3D (32 logical CPUs), 31 GiB RAM, NVIDIA RTX 5070 Ti, Rust 1.99.1, Slint software renderer:

  | Setting | CPU seconds | Average CPU | Working set | Private working set | Private bytes |
  | --- | --- | --- | --- | --- | --- |
  | Default | 0.031, 0.016 | 0.0016%, 0.0008% | 28.3, 27.3 MiB | 8.1, 8.1 MiB | 8.8, 8.8 MiB |
  | `LIGHTCAL_MICA=1` | 0.109, 0.047 | 0.0057%, 0.0024% | 27.3, 27.4 MiB | 8.0, 8.1 MiB | 8.8, 8.9 MiB |

  These are short samples, not the 5 minute protocol above, and they cover only the Lightcal process. Mica is composited by `dwm.exe`, whose CPU and GPU cost was not captured, and it was measured while the backdrop was hidden behind opaque Slint pixels. Measure again once the UI exposes the backdrop.
- `pwsh -NoProfile -File scripts/test-nsis.ps1` exercises the installer and uninstaller with all real-profile operations compiled out, verifying the payload hash and preservation of unrelated files.
